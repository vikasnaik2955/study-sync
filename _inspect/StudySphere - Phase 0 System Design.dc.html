Phase 0 deliverable

Study Group & Notes Sharing Platform

A complete system design for StudySphere — one place for students to share notes, join subject study groups, ask & answer questions, chat in real time, and collaborate in virtual rooms. API-first, so the same backend powers the web app today and an Android app later.

React · MUI · Redux Toolkit Spring Boot · Security · JPA · STOMP PostgreSQL · Flyway JWT access + refresh
00

Overview & assumptions

Six modules ship in v1: auth/profile, notes, study groups, Q&A forum, real-time chat, and virtual study rooms. Three roles — Student (default), Group Owner (a student who owns a group), and a minimal Admin — governed by role-based access control plus per-resource ownership checks.

Assumptions made

Maven + Gradle → Maven
Single build tool chosen and used consistently across all modules.
RTK Query for data
Used for REST caching/fetching; plain slices for auth + socket session state.
Refresh tokens are persisted
Stored hashed in a refresh_token table to support rotation & revoke-on-logout.
UUID primary keys
Client-safe, non-enumerable IDs everywhere; better for a public API surface.
Group chat ↔ study group
A group's chat is a Conversation of type GROUP linked to the group; rooms have their own discussion stream.
STOMP over SockJS
SockJS fallback enabled for the web client; raw WS works for Android.
Out of scope for v1 (designed-for, not built): audio/video calls, CRDT live co-editing, email/push notifications, and the Android client. Nothing below blocks adding these without re-architecting.
01

High-level architecture

A React SPA talks to a stateless Spring Boot API over HTTPS (REST) and WSS (STOMP). The API holds all business logic, persists to PostgreSQL, and offloads binary files to a pluggable storage backend. The future Android client speaks to the exact same two protocols — no web-only logic leaks server-side.

REST API contract

        
Everything is versioned under /api/v1. JSON in, JSON out (uploads are multipart/form-data). Two envelopes are used everywhere — a standard error shape and a standard page shape — so every client (web and Android) parses responses identically.

          04
          
        

        
Real-time design

        
One STOMP endpoint at /ws (SockJS fallback) powers chat, room discussion, and presence. The JWT is validated on the CONNECT frame; the resolved principal is then used to authorize every SUBSCRIBE and SEND, so a user can only join topics they're entitled to.


        

          

            
Subscribe destinations (server → client)

            

              
/user/queue/messages
Private direct-message delivery to the connected user.

              
/topic/conversation/{id}
Messages for a group conversation (members only).

              
/topic/room/{roomId}
Study-room discussion + shared-note events.

              
/topic/presence/{scopeId}
Online/offline + join/leave for a group or room scope.

            

          

          

            
App destinations (client → server)

            

              
/app/chat.send
Send a direct/group message; server persists then fans out.

              
/app/room.post
Post to a room discussion stream.

              
/app/presence.ping
Heartbeat; drives presence with disconnect detection.

              
/app/chat.typing
Transient typing indicator (not persisted).

  "type": "MESSAGE_CREATED",

          05
          
        

        
Security design

        

          
JWT strategy
Access token ~15 min, refresh ~7 days. Refresh rotation: each use issues a new refresh and revokes the old. Tokens stored hashed; logout revokes the family.

          
Password hashing
BCrypt (strength 12). Plaintext never stored or logged. Password change re-hashes and revokes all refresh tokens.

          
RBAC + ownership
Roles STUDENT/ADMIN via @PreAuthorize. Ownership enforced in the service layer — roles are never trusted from the client.

          
CORS
Allowlist the web origin(s) only; credentialed requests; methods + headers scoped. Android uses no CORS (native client).

          
File-upload validation
MIME allowlist (PDF/DOCX/PPT/PPTX), max size cap, filename sanitization + random stored key, and a pluggable virus-scan hook before commit.

          
Rate limiting
Bucket4j on auth (login/register/refresh) and upload endpoints; returns 429 with Retry-After.

        

        
Download endpoints are authorized per-resource and stream via Resource (no full-file buffering). Cloud files are served through short-lived signed URLs, never public buckets.

File storage abstraction

        
A single interface hides where bytes live. Dev uses local disk; prod swaps to S3-compatible or Cloudinary via one config property — no other code changes.

        
public interface StorageService {

    /** Validate + persist a file, returning its stored descriptor. */
    StoredObject store(MultipartFile file, StorageContext ctx);

    /** Open a stream for download (never buffers the whole file). */
    Resource loadAsResource(String storageKey);

    /** Generate a (possibly signed, time-limited) access URL. */
    String url(String storageKey, Duration ttl);

    /** Remove the object; idempotent. */
    void delete(String storageKey);
}

record StoredObject(String storageKey, String url, long size,
                    String contentType, String checksum) {}

// Implementations selected by `storage.provider`:
//   LocalStorageService   → storage.provider=local   (dev)
//   S3StorageService      → storage.provider=s3      (prod)
//   CloudinaryStorage     → storage.provider=cloudinary

        

          
Local (dev)
Writes under storage.local.dir; served via an authorized /download controller.

          
S3 / compatible
Private bucket; pre-signed GET URLs with short TTL. Works with MinIO locally too.

          
Cloudinary
Signed delivery URLs; good if you want managed transforms/CDN later.

DB migration strategy

        
Flyway, versioned SQL, forward-only. JPA runs in validate mode (never ddl-auto=update) so the schema is owned by migrations, not Hibernate. One migration per logical change; never edit an applied file.

        

          

            

              Migration
              Contents
            

            
              
V1__init_users.sqlusers, roles, refresh_tokens + indexes

              
V2__subjects_notes.sqlsubjects, notes (+ subject FK, full-text/title index)

              
V3__groups.sqlstudy_groups, group_memberships, group_notes

              
V4__qa.sqlquestions, answers, votes (unique user+answer)

              
V5__chat.sqlconversations, conversation_participants, messages

              
V6__rooms.sqlstudy_rooms, study_room_participants, room_notes

              
R__seed_subjects.sqlrepeatable seed of default subjects (dev/staging)
